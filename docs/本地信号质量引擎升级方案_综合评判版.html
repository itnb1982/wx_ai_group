万象Ai · 本地信号质量引擎升级方案（综合评判版）

两份参考文案（"LSTM/TCN + Meta-Labeling" 与 "Chronos 换 GBM"）仅作参考。本文基于我亲自海外调研核实的数据源，给出独立综合方案。<br>唯一红线：赚钱、不亏本。任何机制（含硬过滤）只要 walk-forward 验证能提升净盈利即可用；"过度过滤砍利润"作为设计警示，非禁令。

0. 红线解读与验收判官

你的红线是"赚钱、不亏本，其他没有红线"。这改变了评判方式：

  • 唯一验收判官 = 净 P&L > 0、PF > 1、单账户不爆仓。不以胜率 / 夏普 / 回撤美观度为指标。
  • 此前"提准非拦截"的经验教训（2026-07-19 过度过滤曾砍掉利润）不再作为硬性禁令，但作为设计警示：任何过滤机制必须用 walk-forward 验证"确实提升净盈利"才能上架，否则就是变相砍单。
  • 我拥有机制自由度：硬过滤、加权、仓位缩放都可以用——唯一判官是实盘/回测的净盈利。

2. 现有系统真实起点

  • 双模型对抗：云 DeepSeek V4 + 混元 Hy3 → 辩论 → Meta 加权合并。
  • 硬特征护城河：compute_smc / detect_regime 已落地（SMC 机构订单流 + 多周期体制 + 反转哨兵）——这是我们的核心优势，必须保留。
  • 质检引擎已存在：GBM（标称"LSTM/TCN 85%"，实际 AUC 0.64 封顶），meta-labeling 流程已跑通。
  • 风控护盾：L3 篮子浮盈锁利 + 反转哨兵已落地。
  • 近期事故：BUY-only 巨亏（290 笔全 BUY、胜率 28.3%、净亏 -$6,743）。根因是 regime 特征偏置把下跌判上涨，不是模型弱。
关键认知：质量引擎升级是锦上添花，前提是先把核心信号（SMC/Regime）的偏置修稳。否则在歪的方向上做"质量过滤"只会过滤得更精确地向亏钱方向收敛。

3. 我的核心判断：该做 / 不该做

该做

  • 升级质检引擎 GBM → Chronos（提信号质量，守"提准"）。
  • 把"方向预测负担"从 LLM 转移到"价格分布 + 硬特征"，绕开 LLM 方向随机（33%）死局。
  • 保留云 DeepSeek 作质量锚点（8GB 跑不了大模型，云 LLM 不可丢）。
  • 用 walk-forward 盈利闸门 作客观验收，直接落实"不亏本"红线。

不该做

  • 不盲目全切本地（8GB 物理限制 + 小模型方向更弱）。
  • 不把自训 LSTM/TCN 作为第一步（数据抽取 + 训练 + 过拟合风险高，且无必要——Chronos 白送）。
  • 不把 Chronos 配成硬门控却不经验证（可能砍利润，违背红线初衷）。

4. 目标架构（信号质量层升级）

行情(MT5) → SMC/Regime 硬特征(主模型 primary, 高 recall 出候选方向)
           → 双 AI 辩论(云 DeepSeek 锚点 + 本地混元)
           → 信号质量层(Chronos 质检打分)   ← 本次升级点
           → 执行器(仓位缩放 + L3 护盾锁利)

Chronos 插入位置：在"候选信号生成后、下单前"。输入我们的价格序列（可叠加 SMC/Regime 特征）→ 输出未来价格分位数分布 → 提取"上行 vs 下行概率差"作为信号质量分 → 乘进 AI 决策置信 / 仓位系数。

为何不替代 LLM 辩论：Chronos 是通用时间序列模型，不擅长"多模型对抗推理"；它只补"价格分布 sanity-check"这一块，主决策仍由 DeepSeek 锚点 + 硬特征主导。

5. 为什么选 Chronos 而非自训 LSTM/TCN（及何时自训）

选 Chronos 的理由

  • 零训练成本、零数据抽取依赖：即下即用，不像自训要先抽 MT5 历史、做特征、训 walk-forward。
  • 额外送价格分布预测：GBM / 自训 TCN 都只给单点打分，Chronos 给完整分位数分布（"未来 60 根 80% 概率在 X~Y 之间"），可作"该信号质量好不好"的直接依据。
  • Apache-2.0 可商用，本机 3060Ti 跑 small 48M（fp16 ~100MB）/ base 205M（~400MB）都绰绰有余。

自训 TCN 作为兜底路线（不优先）

  • 触发条件：Chronos 在 XAU walk-forward 上 PF 不超 GBM 0.64，或分布外严重（黄金高波动/跳空/三时段动力学不匹配）。
  • 届时启动：MT5 抽 D1/H4/H1/M15 → 特征工程（复用 compute_smc/regime）→ TCN 优先（因果卷积防未来泄漏、GPU/CPU 都快）→ seq_len=60（H1 约 2.5 天）→ Triple-Barrier 标签（基于 ATR）。

6. 部署架构（3060Ti 8GB 现实约束）

  • Chronos 作独立本地推理服务：单独 Python 进程，模型常驻 GPU（~400MB fp16），后端经 localhost HTTP 调用。GPU 内存隔离，N 账号复用同一服务，不重复加载。
  • 不同时在本地跑 7B LLM：8GB 不够"Chronos + 7B LLM + 系统 + MT5 + 浏览器"共存。云 DeepSeek 承担重 LLM 推理。
  • 框架 = PyTorch（Windows GPU 版），非 TensorFlow（Win 原生 GPU 不支持，需 WSL2 徒增复杂度）。
  • 版本路径：先 small 48M 验证，base 205M 若延迟/显存 OK 再上。

7. 赚钱 / 不亏本的硬性验证闸门（守红线）

任何模型上架前必须过这道闸：

  1. walk-forward 5 折，强制覆盖 2020 新冠暴涨 / 2022 加息熊 / 2023 横盘 / 2024 牛市 四态（否则过拟合，实盘必翻车）。
  2. 硬门槛指标：PF > 1.0（一票否决）、净 P&L > 0、单账户最大回撤 < 本金阈值、夏普 > 0。
  3. 标签规范：Triple-Barrier 的 barrier = k×ATR(14)（k≈1.5~2.5，绝不写死 pip）；timeout ≈ 20~30 根；embargo ≥ 信号持有期防泄漏。
  4. 实时机制（守红线同时保 volume）：Chronos 评分低时缩放仓位（非全 block），保留交易笔数保利润；仅当"评分极低 + regime 逆向确认"才硬 block——且此硬 block 须先验证"不伤净盈利"。
  5. 影子运行（A/B）：Chronos 先与 GBM 并行影子跑，确认 PF 真实超越 0.64 再切换为主。

9. 风险与回退

  • Chronos 分布外（XAU 高波动不匹配）：回退 GBM，或启动自训 TCN 兜底。
  • 延迟扛不住 N=10+ 账号：推理服务批处理 / 降频调用 / 升 base 前先压测并发。
  • 任何阶段净 P&L 不达标：回退上一稳定版，绝不带病上架。
  • 核心信号偏置复发：L3 护盾 + regime 校验持续监控，回归 BUY-only 单边即停。
