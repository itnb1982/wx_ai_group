# 万象Ai 智能交易系统 — 端到端架构设计 v6

> **云端双脑 × 本地双核 · 四模型协同决策** ｜ 交易标的 XAU/USD ｜ 商业版

> 目标：结束“哪里漏补哪里”的补丁模式，建立从账号激活、AI 信号、开单执行、仓位管理到策略风控兜底的完整系统。所有模块权责清晰、接口稳定、可扩展至 10+ 账号。

---

## 一、当前混乱根因诊断

### 1.1 职责边界模糊
| 问题 | 表现 | 根因 |
|------|------|------|
| 仓位管理混乱 | 4 个账号有的开仓、有的没开仓；有的平仓、有的没平仓 | `trade_executor.py` 同时承担 AI 决策、开单、跟单、平仓、风控、仓位管理，代码超 2000 行，状态机缺失 |
| 信号同步失真 | 主号平了，跟号没平；主号开了，跟号漏跟 | `_LEADER_EXIT_BUS`、`_LATEST_LEADER_SIGNAL`、`_MIRRORED`、`_LAST_COPIED` 多个全局 dict 并行，幂等/TTL 逻辑不一致 |
| 本金/手数权限链断裂 | 同一账号手数被 `base_capital`、`capital_source`、`balance`、`_cap_to_risk_limit`、`max_lot_per_trade` 多处截断，结果不可预期 | 本金与手数决策散落在 `intelligent_sizing.py`、`risk_engine.py`、`trade_executor.py`，没有单一权威来源 |
| AI 看不到本地模型 | 前端“人话解读”里只提 DS/HY，未把 Chronos 和质量陪审团结论融入 | `_build_plain_summary` 仅在特定场景才提示 Chronos，未作为固定决策 provenance 展示 |
| 扩展性差 | 周期偶发 180s 超时 | 并发粒度仍以“用户”为单位，内部跟号串行，账号数增加后必然超时 |

### 1.2 核心设计缺陷
- **无统一执行控制器**：开单、加仓、减仓、平仓、对账各自为政，没有“账号级状态机”。
- **风控与 AI 决策混排**：AI 决策后又叠加多层门控（体制门、空头约束、置信惩罚），这些本应是风控兜底的职责，现在反而干扰 AI 信号。
- **跟号逻辑与主号逻辑耦合**：跟号既要做镜像，又要跑自己的风控，导致状态不一致。

## 二、目标架构总览

### 2.1 五层架构

```text
┌─────────────────────────────────────────────────────────────┐
│  第①层：接入与账号管理                                        │
│  AccountManager → MT5 终端激活 → Worker 生命周期              │
├─────────────────────────────────────────────────────────────┤
│  第②层：行情与信号层                                          │
│  MarketDataService + Chronos + MetaQuality + ReversalSentinel │
├─────────────────────────────────────────────────────────────┤
│  第③层：AI 决策大脑                                           │
│  DebateEngine(DS/HY) + MetaAgent + 本地时序第三票              │
├─────────────────────────────────────────────────────────────┤
│  第④层：执行控制层（新增）                                    │
│  ExecutionController(账号级状态机) + SignalBus(事件总线)       │
├─────────────────────────────────────────────────────────────┤
│  第⑤层：策略风控兜底                                          │
│  RiskEngine(6层物理风控) + SmartExit/AIExit                   │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 关键原则
1. **单一权威**：每个账号的“有效本金”“有效手数范围”“当前持仓”只能有一个权威来源。
2. **风控兜底最大**：风控层拥有最终否决权；AI 与风控冲突时，风控赢，且必须留下审计日志。
3. **AI 只负责信号与意图**：AI 输出方向、置信、仓位意图（open/add/reduce）、目标风险%；具体开不开、开多少由执行控制器在风控框架内执行。
4. **账号级隔离**：每个账号独立状态机、独立缓存、独立风控；账号之间只通过 SignalBus 传递 leader 信号。
5. **多租户风险域隔离**：**一个账号 = 一个独立客户**（详见 7.0）。风险与资金只在"同一客户的主号+跟号"内合并计算，**跨客户绝不合并**。平台层只熔断信号源，不干预客户持仓（详见 9.3 / 9.4）。
6. **可观测**：任何被拦截、被修改、被同步的事件都进入前端事件流，客户一眼看懂。

## 三、模块权责矩阵

| 模块 | 核心职责 | 不做什么 | 关键输出 |
|------|----------|----------|----------|
| **LicenseService** | 客户端授权激活、机器指纹绑定、到期/配额校验、离线宽限裁定 | **授权失效只停开新仓，绝不强平持仓**（商业契约≠风控） | `LicenseStatus` |
| **AccountManager** | 账号 CRUD、终端路径校验、MT5 连接/断开、Worker 启停 | 不参与交易决策 | 账号连接状态、实时余额 |
| **ReconcileService** | 每周期强制对账 MT5 ↔ 本地账本，检出并修复四类漂移 | 不擅自平掉 MT5 上的孤儿单，只补录纳管 | `ReconcileReport` |
| **MarketDataService** | 统一行情快照（OHLCV、ATR、Regime、延伸度、RSI） | 不下单、不风控 | `MarketSnapshot` |
| **ChronosService** | 本地时序预测 P10/P50/P90 | 不直接开单 | `chronos_forecast` |
| **MetaQuality** | 信号质量分 Q、Chronos 方向、止盈 regime | 不拦截开仓 | `MetaQualityReport` |
| **DebateEngine** | 双模型辩论、注入账号持仓/历史成交、输出决策 | 不碰仓位管理 | `DebateDecision` |
| **MetaAgent** | 加权裁决、Chronos 第三票、仓位意图 | 不直接下单 | 含 `position_intent`、`target_risk_pct` 的决策 |
| **SignalBus** | 主号信号/出场动作发布，跟号订阅 | 不解释信号含义 | 事件队列（幂等 key） |
| **ExecutionController** | 账号级状态机：对账→决策→风控→下单→持仓管理→平仓 | 不替代 AI 决策 | 订单、持仓变更、事件日志 |
| **RiskEngine** | 6 层风控硬检查，拥有最终否决权；作用域限于**单账号**或**同一客户的风险域**（主号+跟号） | 不主动开仓、**不跨客户合并资金** | `RiskCheckResult` |
| **PlatformHealthMonitor** | 信号源健康度监控、**降级车道档位裁定（L0/L1/L2/L3）**与平台级熔断 | **不碰任何客户资金、不强平任何持仓** | `SignalSourceHealth`、`DegradeLevel`、熔断事件 |
| **LocalLLMService** | 本地 Qwen3 8B（Ollama）：L0 做结构校验/矛盾检测（校对员），L1/L2 降权补位投票（副驾） | **禁止在 L0 参与方向投票**（8B 金融方向准确率近随机）；不绕过风控 | `LocalOpinion`（含降权系数）、`SanityCheckResult` |
| **EmergencyConsole** | **人工**紧急处置通道：E1 单仓 / E2 单账号 / E3 风险域 / E4 全体一键平仓 + `MANUAL_HALT` | **绝不自动触发**（只响应自然人指令）；不做行情判断、不做策略决策 | 处置执行报告、不可变审计日志 |
| **SmartExit/AIExit** | 持仓级出场计划（分批、追踪、保本、反转） | 不绕过风控执行 | `ExitPlan` |
| **FollowerEngine** | 消费 leader 信号；若被设为主号的跟号，则复制订单/镜像出场，并以主号口径覆盖自身本金/手数/日 DD 逻辑 | 不独立辩论 | 跟单结果 |
| **Frontend** | 展示决策溯源、账号仓位、风控事件 | 不修改后端逻辑 | 可视化面板 |

## 四、数据流：一个完整决策周期

```text
1. MarketDataService 采集行情
        ↓
2. DebateEngine 注入【本账号】持仓/成交 → DS/HY 辩论
        ↓
3. MetaAgent 综合 DS/HY/Chronos/Regime/Sentinel → DebateDecision
        ↓
4. ExecutionController 接收 DebateDecision
        │
        ├─ 4a. 反向对账：MT5 持仓 ↔ 本地账本
        ├─ 4b. 计算有效本金、目标手数区间
        ├─ 4c. 风控审核（RiskEngine 拥有否决权）
        ├─ 4d. 执行开/加/减/平
        └─ 4e. 记录事件 + 发布 SignalBus
        ↓
5. SmartExit/AIExit 为每笔持仓生成 ExitPlan
        ↓
6. ExecutionController 执行出场/移损，并广播 leader 动作
        ↓
7. FollowerEngine 接收广播 → 镜像到跟号
```

## 五、执行控制器：账号级状态机

### 5.1 核心数据结构

```python
class AccountPortfolio:
    account_id: str
    user_id: str
    positions: List[Position]          # 当前真实持仓（MT5 对账后）
    total_lots: float
    total_floating_pnl: float
    direction_counts: Dict[str, int]   # BUY/SELL 各几笔
    capital: EffectiveCapital          # 见 5.2
    lot_bounds: LotBounds              # 见 5.3
    state: AccountState                # idle/reconciling/repairing/deciding/
                                       # placing/open/managing/exiting/
                                       # blocked/manual_halt
    last_reconciled_at: datetime       # 上次成功对账时间
    drift_count: int                   # 本周期检出的账本漂移笔数
    license_ok: bool                   # 授权校验结果（见第十一章）

class Signal:
    direction: str                     # BUY / SELL / HOLD
    confidence: float
    intent: str                        # open / add / reduce / hold
    target_risk_pct: Optional[float]   # AI 建议风险%
    sl: float
    tp: float
    quality: MetaQualityReport

class OrderIntent:
    direction: str
    lots: float
    sl: float
    tp: float
    reason: str                        # 决策链路说明
    risk_check: RiskCheckResult
```

### 5.2 本金权限链（单一权威）

```text
effective_capital =
    用户输入本金(input_capital)  if input_capital > 0
    else strategy.base_capital    if capital_source == "manual" and base_capital > 0
    else MT5 实时 balance
```

- **用户输入本金权限最大**：前端“本金入金”输入框一旦有值，所有手数/风控缩放以该值为准。
- **未输入时**：`base_capital`（手动模式）> `balance`（实时模式）。
- **风控仍读取真实余额**：日亏损、回撤熔断必须基于真实 `equity/balance`，不能基于输入本金造假。

### 5.3 手数权限链（单一权威）

```text
raw_lots = f(effective_capital, signal_confidence, ATR, same_direction_count, intent)
allowed_lots = clamp(raw_lots,
                     hard_floor = user_min_lot,      # 单笔硬底，不可突破
                     hard_ceil  = user_max_lot)      # 单笔硬顶，不可突破
final_lots = min(allowed_lots,
                 risk_engine_max_single_lots,
                 risk_engine_max_position_lots_remaining)   # 同方向总持仓剩余额度
```

- **用户输入的最低/最高手数是单笔硬边界**，任何情况下不得突破。
- **同方向总持仓上限 `max_position_lots` 是第二硬边界**：已开仓 + 新开仓 ≤ `max_position_lots`。例：`max_position_lots=1`，第一单 BUY 0.2，AI 判断信号晴朗，第二单 BUY 0.5，总持仓 0.7 ≤ 1，**允许**。
- **中间空间由行情决定**：信号置信高、ATR 低、趋势强、意图为 `add` → AI 可在 `[min_lot, max_lot]` 内偏向上限给出更大的单笔；反之偏向低点。
- **AI `target_risk_pct` 在风控框架内可调高调低**：上调受限于 `max_risk_per_trade_pct` 和单笔/总持仓硬顶；下调用于主动收缩风险。不是只能下调。

### 5.4 状态机转换

```text
IDLE ──周期开始──▶ RECONCILING          (强制入口，不可跳过)
RECONCILING ──账本一致──▶ DECIDING
RECONCILING ──发现漂移──▶ REPAIRING ──修复完成──▶ DECIDING
DECIDING ──风控通过──▶ PLACING
PLACING ──下单成功──▶ OPEN
OPEN ──周期触发──▶ MANAGING
MANAGING ──出场条件满足──▶ EXITING
EXITING ──平仓完成──▶ IDLE

任意状态 ──人工紧急指令──▶ MANUAL_HALT   (插队，最高优先级)
MANUAL_HALT ──人工解除──▶ IDLE            (系统永不自动恢复)
```

任何状态遇到风控否决 → `BLOCKED` → 记录原因 → 回到 IDLE。

#### RECONCILING 是强制第一步（★ 补充：原状态机遗漏）

数据流 4a 定义了「反向对账」，但状态机原先直接 `IDLE → DECIDING`，等于**允许系统在不知道自己真实持仓的情况下做决策** —— 这正是"有的开了有的没开、有的平了有的没平"的结构性来源。现修正为：**每个周期必须先经过 `RECONCILING`，禁止跳过**。

对账比对三组数据，任一不一致即进入 `REPAIRING`：

| 比对项 | 权威源 | 漂移典型成因 |
|---|---|---|
| 持仓列表（ticket 集合） | **MT5 实际持仓** | 下单超时但实际成交、手动干预、跟号漏跟 |
| 每笔手数与方向 | **MT5 实际持仓** | 部分平仓未回写本地账本 |
| SL/TP 实际挂载值 | **MT5 实际持仓** | 移损失败但本地已标记成功 |

**权威源永远是 MT5，不是本地账本。** 本地记录与 MT5 冲突时，无条件以 MT5 为准并改写本地。

`REPAIRING` 的四类修复动作：

| 漂移类型 | 修复动作 |
|---|---|
| MT5 有、本地无（孤儿单） | 补录进本地账本，纳入后续管理，**不擅自平仓** |
| 本地有、MT5 无（幽灵单） | 删除本地记录，记审计事件 |
| 手数/方向不符 | 以 MT5 为准覆写本地 |
| SL/TP 缺失或不符 | 按当前 ExitPlan 重新挂载 |

> 对账失败（如 MT5 查询超时）时**不得进入 DECIDING**，本周期直接跳过并告警 —— 宁可少做一单，不可盲开一单。

`MANUAL_HALT` 是唯一由**自然人**驱动进出的状态：进入时立即冻结开仓并逐单平仓，期间 AI 信号照常记录但执行层一律拒绝开新仓，剩余持仓的 SL/TP/SmartExit 仍继续生效。详见 **9.6**。

## 七、多账号扩展模型

### 7.0 业务前提：一个账号 = 一个客户（风险域边界定义）

> **这是全系统最重要的前提，任何风控/仓位/统计模块都必须遵守。**

本系统的"多账号"是**多租户（multi-tenant）业务形态**，不是"同一个人开多个子账号"：

- **N 个交易账号 = N 个彼此独立的客户**，资金无关联、法律主体独立。
- **N 完全由客户数量决定**，是纯变量（可能是 1，也可能是 50+）。任何模块**禁止**假设固定账号数、禁止写死列表长度。
- **唯一例外**：同一客户可同时拥有 1 个主号 + 若干跟号（见 7.3）。这一组账号属于**同一个客户**，才可以合并计算风险。

由此，系统存在三级实体，风控作用域必须严格对应：

| 实体层级 | 范围 | 说明 |
|---|---|---|
| **账号（Account）** | 单个 MT5 账号 | 最小执行单元，独立 Worker、独立状态机 |
| **风险域（Risk Domain）** | 同一 `owner` 的主号 + 跟号 | **唯一允许合并计算资金风险的边界** |
| **平台（Platform）** | 所有客户全体 | **绝不合并客户资金**，只做信号源健康与运营监控 |

### 7.1 并发粒度
- **旧模型**：每用户一个线程，内部串行处理所有账号。
- **新模型**：每个活跃交易账号一个 `ExecutionController` 实例，由账号级线程池调度。
- 主号先决策，但通过 SignalBus 异步解耦，跟号不必等待主号完成全部流程。

### 7.2 10+ 账号扩展要点
- 每个账号独立 Worker 进程（已具备）。
- 每个账号独立数据库会话，禁止跨线程共享 SQLAlchemy Session。
- 决策缓存按 `account_id` 隔离（已修复）。
- SignalBus 事件 TTL + 幂等 key，防止事件积压。

### 7.3 主号与跟号权限覆盖规则

当用户显式指定某账号为**主号(leader)**，其他账号为**跟号(follower)**时：

| 权限项 | 主号 | 跟号 |
|--------|------|------|
| 本金来源 | 自身 `effective_capital` | **跟随主号**的 `effective_capital` 与日 DD 计算口径 |
| 单笔手数范围 | 自身 `min_lot / max_lot` | **跟随主号**的 `min_lot / max_lot` |
| 总持仓上限 | 自身 `max_position_lots` | **跟随主号**的 `max_position_lots` |
| 日亏损/回撤熔断 | 自身风控 | **跟随主号**的日 DD 逻辑与阈值 |
| AI 辩论 | 独立运行 | 不独立辩论，直接消费主号 SignalBus 信号 |
| 出场动作 | 独立生成并广播 | 镜像主号的出场事件 |

- **取消跟号关系后**：跟号立即恢复自身策略配置（本金、手数范围、风控阈值），下一周期起按自身参数独立执行。
- **技术实现**：`FollowerEngine` 在启动时读取 `leader_account_id`；若存在，则从主号 `AccountPortfolio` 复制 `EffectiveCapital` 与 `LotBounds` 的**计算口径**，而不是复制主号余额数字（主号 $10k、跟号 $1k 时，跟号仍按 $1k 真实本金等比缩放，但边界比例与主号一致）。

## 八、AI 决策溯源：让本地模型“被看见”

### 8.1 Meta 裁决卡片必须展示
- **DeepSeek 投票**：方向 + 置信 + 权重
- **混元投票**：方向 + 置信 + 权重
- **Chronos 投票**：方向（BUY/SELL/HOLD）+ 权重 + 是否可用
- **本地时序质量分 Q**：80 分对应的 `HIGH/MID/LOW/VERY_LOW`
- **P10/P50/P90**：可视化未来价格分位数
- **共识类型**：strong / moderate / disagreement

### 8.2 人话解读模板
```text
“DeepSeek 看涨 71%，混元看涨 70%，本地 Chronos 也看涨，三模型共振；
 信号质量 80 分（HIGH），P90 目标 4295。当前处于 uptrend，AI 意图=open，
 建议按行情给到手数区间中上限，风控兜底已就位。”
```

## 九、策略风控兜底：最高权限

### 9.1 风控层职责
- 点差、持仓笔数、持仓手数、同方向并发、日亏损、回撤、单笔风险、交易时段。
- **任何一层未通过，交易被否决**，并生成前端可见的“风控拦截”事件。

### 9.2 与 AI 的冲突规则
| 场景 | 处理 |
|------|------|
| AI 要开仓，风控通过 | 正常执行 |
| AI 要开仓，风控否决 | 否决，记录原因，不改变持仓 |
| AI 要加仓，风控提示仓位已满 | 降级为 `reduce` 或 `hold` |
| AI 要平仓，风控通过 | 正常执行 |
| 风控触发硬止损/熔断 | 无视 AI，直接平仓，记录为“风控兜底” |
| **人工紧急指令（L-M）** | **无视 AI、无视风控评估、插队执行，最高优先级**（见 9.6） |

### 9.3 风控作用域三层模型（★ 重要修正）

> **修正说明**：早期讨论中曾提议增加"跨账号组合级日损总闸"（所有账号当日合计亏损触线全停）。
> 在确认业务前提为"一账号一客户"后，**该提案作废**。跨客户合并资金风控是**错误且危险**的设计。

| 作用域 | 计算范围 | 是否合并资金 | 触发后动作 |
|---|---|---|---|
| **L-A 账号级** | 单账号自身 | — | 该账号停止开仓 / 触发强平 |
| **L-B 风险域级** | 同一客户的主号 + 全部跟号 | ✅ **合并** | 该客户名下全部账号停止开仓 |
| **L-C 平台级** | 全体客户 | ❌ **绝不合并** | 只熔断**信号发布**，不动任何客户持仓 |

**为什么绝不做跨客户资金合并熔断：**

1. **资金无关联**：客户 A 亏损与客户 B 毫无关系。用 A 的亏损去停 B 的单，等于无故剥夺 B 的交易机会，会直接引发投诉与赔付纠纷。
2. **合规红线**：不同客户资金必须独立核算。合并风控口径 = 把独立账户当成一个资金池处理。
3. **阈值不可定义**：日损"总额"会随客户数线性膨胀。10 个客户和 100 个客户的"合计亏损线"没有任何可比性，参数无法设定。

**风险域级（L-B）合并的合法性**：主号 + 跟号本就是同一客户的资金，且跟号本就继承主号的本金口径与日 DD 逻辑（7.3），合并计算是自洽的。

**★ 补充：以上 L-A / L-B / L-C 三层全部是「系统自动」判定。系统之外还存在第四个授权来源 —— 人。**

| | 授权来源 | 判定者 | 可否处置客户持仓 |
|---|---|---|---|
| L-A / L-B | 算法（阈值触发） | 系统 | ✅ 在客户已授权的风控规则内 |
| L-C 平台熔断 | 算法（健康度触发） | 系统 | ❌ **绝对禁止**（见 9.4.2） |
| **L-M 人工紧急处置** | **自然人主动按下** | **运维人员** | ✅ **可以，且优先级最高**（见 9.6） |

L-M 不是风控规则，是**人工干预通道**。系统永远不会自己触发它。详见 **9.6**。

### 9.4 平台级熔断：熔的是"信号源"，不是客户资金

虽然禁止合并客户资金，但**所有客户消费同一个 AI 信号源（XAUUSD）**，这构成真实的系统性风险 —— 风险来源不是资金相关性，而是**信号源相关性**。信号源一旦失灵，全体客户会同时亏损，这是平台方的责任风险。

**触发条件（全部基于信号源自身健康度，与任何客户资金无关）：**

| 触发项 | 判据 |
|---|---|
| 信号连败 | 平台级**信号**（跨客户去重后，非订单数）连续 N 次以止损收场 |
| 模型不可用 | DeepSeek / 混元 / Chronos 任一持续超时或返回异常 |
| 行情异常 | 行情源断线、tick 停滞、点差异常扩大 |
| 鞭锯识别 | 单位时间内方向反转次数超阈 |

#### 9.4.1 五个真实触发场景（判据的具体形态）

**场景 A — 云模型半瘫（最高频）**
凌晨 DeepSeek 服务端 503 / 欠费停服 / 限流。DS 与 HY 权重各 0.5，DS 一挂，裁决实际退化为「混元一人说了算」，若代码给缺席方填中性默认值参与加权，等于**半个大脑在下单**。此刻全体客户会同时按这个瘸腿决策开仓。

**场景 B — 数据事件点差爆炸**
北京时间 20:30 非农 / CPI 公布瞬间，XAUUSD 点差从 ~20 跳到 400+。AI 拿到的是失真价格，算出的 SL/TP 距离全错，任何客户此刻进场都是先亏几十美金起步。

**场景 C — 报价冻结（最阴险，不报错）**
MT5 连接显示「在线」，但 tick 停止更新，同一 bid/ask 卡住 90 秒。Chronos 用这段死数据出的 P10/P50/P90 全是垃圾，SMC 会误判为「极度盘整」。**系统不会抛异常，它会自信地给出一个完全错误的信号。**

**场景 D — 信号连败（计数口径是关键）**
必须**按信号 ID 去重**：同一信号无论被多少客户执行，胜负只算 1 次。若按订单计数，10 个客户跟一个信号 → 一次失败产生 10 笔亏损单 → 「连败 3 次」瞬间触发，**客户越多越容易误熔断**。这与已作废的「跨账号合计损失线」是同一类错误（阈值随客户数膨胀），不得重犯。

**场景 E — 方向鞭锯**
DS/HY 在 0.5 低置信下反复翻转（BUY→SELL→BUY）。短时高频翻向说明模型已在噪声中迷失，属模型状态问题而非某个客户的问题（本项目已有实证亏损记录）。

**触发后动作（关键：只作用于信号层）：**

- ✅ **停止发布新开仓信号** —— 所有客户都不再收到新单；
- ✅ **不强平任何客户持仓** —— 已有仓位交回各账号自身风控（SL/TP/SmartExit/篮子兜底）处理；
- ✅ 前端全局横幅告警 + 运营侧通知；
- ✅ 恢复需人工确认，或健康度连续 M 个周期正常后自动恢复。

> 一句话：**平台熔断只关水龙头，不抽走客户已经接到桶里的水。**

#### 9.4.2 为什么只能停信号、不能强平（红线依据）

类比：**交易所熔断 = 暂停撮合，不是替你把股票卖掉**；替客户处置资产是券商强平，性质完全不同。本平台的角色是「信号供应商」，只能停止供货。

| 红线 | 理由 |
|---|---|
| 已开仓是客户资产 | 平台无权处置，强平引发赔付纠纷与合规风险 |
| 客户自设规则仍有效 | SL/TP/SmartExit/篮子是客户**已授权**的处置规则，熔断期间照常运行 |
| 客户手动权不受限 | 熔断期间客户仍可自行操作本人账号 |

#### 9.4.3 与「多交易多赚钱」铁律不冲突

熔断**只在大脑故障 / 数据脏污时触发**，此刻信号期望为负 —— 这是**拒绝在故障状态下瞎下单**，不是「过滤好信号」。二者本质区别：

- ❌ 多层过滤：好信号被门槛砍掉 → 交易笔数↓、利润↓（已多次验证失败）
- ✅ 故障熔断：坏信号根本不该产生 → 保护利润，且持续时间为分钟级（API 恢复即恢复），非常态

**因此熔断不计入「过滤」范畴，不受「提准非拦截」铁律约束。**

#### 9.4.4 ★ 降级车道：熔断不该只有「停」一个档位（本地模型兜底）

**问题**：9.4 定义的熔断是二值的 —— 要么全绿正常跑，要么全红停摆。但现实中最高频的故障（场景 A：单家云模型 503/限流）并不需要「全停」，那是**过度反应**，会白白损失交易笔数，违背「多交易多赚钱」。

**业界标准做法**：LLM Waterfall Pattern（瀑布降级）—— Tier1 主 API → Tier2 备用 → **Tier3 本地模型兜底**。核心是「渐进降级（graceful degradation）」而非「二值开关」。多家生产实践一致给出的降级链形态为：`缓存 → 主模型+重试 → 备用模型 → 本地小模型 → 静态兜底`。

**本系统四级降级车道：**

| 级别 | 触发条件 | 可用大脑 | 手数系数 | 允许动作 |
|---|---|---|---|---|
| **L0 全绿** | DS / 混元 / Chronos 全部正常 | DS 0.5 + 混元 0.5 + Chronos 第三票 0.25 | ×1.00 | 正常开仓 / 加仓 / 减仓 / 平仓 |
| **L1 补位** | DS **或** 混元单边故障（超时/限流/5xx） | 存活云模型 + **本地 Qwen3 8B（权重 0.3）** + Chronos | **×0.60** | 可开仓，但**方向必须与 Chronos P50 同向**；禁止逆势加仓 |
| **L2 接管** | 两家云模型**全部**不可用，本地仍在 | **本地 Qwen3 8B + Chronos 两票** | **×0.30** | **只守不攻**：禁开新方向；仅允许「同向减仓 / 平仓 / 移动止损」；仅当本地与 Chronos **方向一致且 Q≥0.65** 时才允许极小仓位顺势加仓 |
| **L3 停摆** | 本地也不可用，**或**报价冻结 / 点差爆炸 / 行情断线 | 无 AI 参与，纯规则 | ×0 | **停发一切开仓信号**；SL/TP/SmartExit/篮子/客户手动**全部照常** |

**降级与恢复的迟滞（防抖动，避免在 L0/L1 之间高频横跳）：**

| 参数 | 值 | 依据 |
|---|---|---|
| 单次调用超时 | 15s | 业界熔断器通行值 |
| 错误率触发阈值 | 滑动窗口 2min 内错误率 > 5% | resilience4j / opossum 默认量级 |
| 降级生效 | 连续 2 个决策周期判定故障 | 防单次抖动误降级 |
| 恢复上升 | 连续 3 个周期健康 + 探针成功 | 恢复比降级更保守（半开态探测） |
| 降级告警 | fallback 触发率 > 5% 即告警 | 备用模型频繁被调用 = 主模型有问题 |

#### 9.4.5 ★ 本地模型的角色边界（必须严格限定，否则会亏钱）

**这是最关键的一条：本地 8B 不是「小一号的 DeepSeek」，它的能力是偏科的。**

依据 Fin-Bias（ACL 2026）等研究：**7B~8B 级模型在金融方向预测上的准确率接近随机**。因此：

| 任务类型 | 本地 8B 是否胜任 | 在本系统中的用法 |
|---|---|---|
| **方向预测**（涨/跌） | ❌ 近随机 | **禁止**作为 L0 正常模式的等权投票者。仅在 L1/L2 降级时以**降权 + 强约束**参与，且必须与 Chronos 同向 |
| **结构化校验** | ✅ 胜任 | **L0 常态启用**：校验云模型返回 JSON 结构合法性 |
| **自相矛盾检测** | ✅ 胜任 | **L0 常态启用**：识别「方向=BUY 但理由文本全在描述下跌」这类逻辑冲突 |
| **幻觉价格检测** | ✅ 胜任 | **L0 常态启用**：比对 AI 口述的支撑/阻力位与真实行情，偏离超阈即标记 |
| **降级期保守决策** | ⚠️ 受限可用 | 仅 L1/L2，且叠加手数系数 + Chronos 同向 + Q 门槛三重约束 |

> **定性：本地模型在 L0 是「校对员」（守门，不投票），在 L1/L2 才临时兼任「副驾」（降权投票，受限动作）。** 这样既拿到了可用性收益，又不让偏科能力污染正常模式的决策质量。

**选型与落地参数（基于本机实测显存定死，非估算）：**

本机实测：RTX 3060 Ti，总显存 8192 MiB，**空闲 6493 MiB**（Windows 桌面 + Chronos-2 常驻已占 1532 MiB）。

| 项 | 取值 | 理由 |
|---|---|---|
| 运行时 | Ollama | 生态成熟，`keep_alive` 可控显存占用 |
| 主选模型 | **`qwen3:8b`（Q4_K_M，约 5.0 GB）** | 2026 年 8GB 档位公认最强；Apache 2.0 可商用；双思考模式；中文强 |
| 备选（显存告急） | `qwen3:4b`（约 3.0 GB） | L3 前的最后一档兜底 |
| `num_ctx` | **4096** | 8K 会让 KV cache 涨到 ~1.0GB，逼近 6.5GB 上限；金融决策 prompt 不长，4K 足够 |
| `keep_alive` | **30m** | 降级期间常驻避免反复加载；恢复后自动释放显存 |
| 思考模式 | **强制 `/no_think`** | 保证响应 <5s，不撑爆 60s 决策周期 |
| `temperature` | **0.3** | 金融决策要稳定复现，不要发散 |
| 输出格式 | 强制 JSON schema | 与云模型输出结构对齐，可直接进裁决器 |

**显存预算核算**：模型权重 5.0 GB + KV cache(4K) ≈ 0.45 GB ≈ **5.45 GB < 6.49 GB 空闲**，留约 1 GB 缓冲。✅ 可行。

> 注意：本地模型**仅在降级时加载**。L0 常态下的「校对员」任务用 `qwen3:4b` 或直接用规则实现，避免长期占用显存影响 Chronos-2 推理。

### 9.5 多客户同标的的执行层风险（真实存在，必须处理）

N 个客户在同一秒对同一品种下市价单，会产生与"资金相关性"无关的**执行侧**问题：

| 问题 | 后果 | 处理方案 |
|---|---|---|
| 同价位挤单 | 后成交账号滑点更差（1 号 4250.1，5 号 4250.6） | **执行错峰**：账号间下单随机抖动 200~800ms |
| 券商侧识别 | 同策略同时下单可能被风控标记 | 错峰 + 手数差异化（各客户本金/手数本就不同） |
| 滑点无归因 | 无法判断亏损来自策略还是执行 | 每单记录**期望价 vs 实际成交价**，纳入审计 |

> 明确**不采用**"限价单排队"方案：黄金波动剧烈，限价挂单漏单率高，会直接减少交易笔数，违背"多交易多赚钱"铁律。

### 9.6 ★ 人工紧急处置窗口（Operator Emergency Console）

> **定位：这不是风控规则，是给运维人员的人工干预通道。系统永远不会自己按这个按钮。**
> 算法负责 7×24 自动运行，人负责在算法覆盖不到的异常里做最终决断。任何成熟的自动交易系统都必须给"人"留一个出口。

#### 9.6.1 与 9.4.2「平台不得强平」是否矛盾？—— 不矛盾，区别在授权来源

| | 9.4.2 禁止的 | 9.6 允许的 |
|---|---|---|
| 谁决定 | **算法**自动判定 | **自然人**主动按下 |
| 是否可追责到人 | 否（无人授权） | 是（身份+IP+时间+理由全留痕） |
| 客户视角 | "系统莫名其妙把我平了" | "平台运维在异常中做了紧急处置，有记录可查" |

> 一句话：**禁止的是「机器擅自动客户的钱」，不是禁止「人在紧急情况下负责任地处置」。**

这在行业里是**监管强制项**，不是可选功能：
- 美国 SEC Rule 15c3-5（市场准入规则）要求具备直接市场准入的机构必须有**人工 kill switch**；
- 欧盟 MiFID II RTS 6 明确要求算法交易系统必须具备 **kill functionality**，可即时撤销未成交订单并中止交易；
- 各大交易所（CME/ICE）均提供并要求会员配置 kill switch。

**所以「一键平仓」不是我们的额外发明，是商业化交易系统的准入门槛。**

#### 9.6.2 四级处置粒度

| 级别 | 作用范围 | 典型使用场景 |
|---|---|---|
| **E1 单仓位** | 指定 `ticket` 单笔平仓 | 某一单明显异常（错误方向 / 手数异常 / 长期挂着不动） |
| **E2 单账号** | 该账号全部持仓平仓 | 单个客户账号异常；客户来电要求立即清仓 |
| **E3 风险域** | 某客户主号 + 全部跟号 | 该客户整体撤退；跟单链出现不一致 |
| **E4 全体** | 平台所有账号全部持仓 | 极端行情（闪崩/跳空）、系统重大故障、券商侧异常 |

**每一级都配两个独立开关：**

| 开关 | 含义 | 不带此开关的后果 |
|---|---|---|
| `close_positions` | 平掉范围内持仓 | — |
| `halt_after` | 平仓后**置为停止开仓**状态 | ⚠️ 平完下一周期 AI 又开回来，等于白平 |

> **默认强制勾选 `halt_after`**。只平不停必须由操作人显式取消勾选，防止"平了又开"的荒谬场景。

#### 9.6.3 执行语义（关键：避免与自动系统打架）

```text
1. 人按下按钮
2. 立即将范围内账号置为 MANUAL_HALT 状态（先冻结，再动手）
3. 快照当前持仓（ticket / 方向 / 手数 / 浮盈亏）→ 写审计日志
4. 逐单发送平仓指令（绕过 AI 与风控评估，人工授权即最高权限）
5. 生成执行报告：逐单成功/失败/滑点/耗时
6. 失败单自动重试 N 次；仍失败则高亮告警，绝不静默失败
```

**`MANUAL_HALT` 状态下的行为约定：**

| 项目 | 行为 |
|---|---|
| AI 信号 | **照常产生、照常记录**（不影响信号统计与后续复盘） |
| 新开仓 | ❌ 执行层一律拒绝 |
| 剩余持仓的 SL/TP/SmartExit/篮子 | ✅ **继续有效**（不能因为停了就让残余持仓裸奔） |
| 客户手动操作 | ✅ 不受限制 |
| 恢复方式 | **只能人工解除**，系统永不自动恢复 |

> 系统自动恢复 = 等于没停。这一条不可妥协。

#### 9.6.4 防误触设计（这个按钮按错就是灾难）

| 机制 | 说明 |
|---|---|
| **影响面预览** | 确认弹窗必须显示：将平 N 个账号 / M 笔持仓 / 当前浮盈亏合计 $X |
| **二次确认** | E1/E2/E3 需勾选确认；**E4 额外要求二次凭据**（操作密码或 TOTP） |
| **理由必填** | 无理由不可提交，理由进审计日志 |
| **幂等 + 防重入锁** | 同一 scope 的处置请求带幂等 key，连点不会重复发单 |
| **不可变审计** | 操作人 / IP / 时间 / 范围 / 理由 / 逐单结果 → 追加写，不可修改删除 |
| **物理隔离** | 前端置于独立红色危险区，与常规操作区分离，不与"启动/暂停"等常用按钮相邻 |

#### 9.6.5 与 ExecutionController 的关系

- 紧急指令是**最高优先级消息**，插队到账号状态机队首，无视当前周期正在做什么（哪怕正在 DECIDING/PLACING）。
- 若指令抵达时正有订单在途（PLACING 未返回），**先等该单返回结果再平**，避免"平了个还没成交的单"导致状态错乱。
- 状态机新增终态 `MANUAL_HALT`，只能由人工指令进入、由人工指令退出。

#### 9.6.6 接口与实现要点

```text
POST /api/emergency/close
{
  "scope":   "ticket" | "account" | "domain" | "all",
  "target":  <ticket_id | account_id | owner_id | null>,
  "halt_after": true,               // 默认 true
  "reason":  "闪崩行情，紧急清仓",   // 必填
  "idempotency_key": "<uuid>"
}

POST /api/emergency/resume        // 解除 MANUAL_HALT，同样需要身份与理由
GET  /api/emergency/audit         // 审计日志查询
```

- 平仓走 `MT5Service` 直接下单，**绕过 AI 与风控评估**（人工授权已是最高权限），但仍受物理约束（不能平不存在的单、市场关闭时须报错而非假装成功）。
- 该接口需**独立权限位**（`ops:emergency`），普通账号登录不可见、不可调用。

### 10.1 品牌定位与 LOGO

#### 10.1.0 软件全称与副文体系（★ 品牌核心，全站唯一权威）

**软件全称（正式名，唯一）**

```text
万象Ai 智能交易系统
```

- 「万象」= 品牌名；「Ai」采用**首字母大写 + i 小写**的固定写法，不得写成 `AI` / `ai` / `A.I.`
- 「智能交易系统」= 品类词，已包含产品属性，副文因此**不再重复交易属性**，专职承载技术亮点

**副文定稿（主副文）**

```text
云端双脑 × 本地双核 · 四模型协同决策
```

**为什么是「双脑 × 双核」而不是直白说「四个模型」**

罗列四个模型名只是堆料，说不清"为什么需要四个"。「双脑 × 双核」把四模型拆成**两种本质不同的智能形态**，一句话讲清架构价值：

| 分组 | 成员 | 智能形态 | 不可替代性 |
|---|---|---|---|
| **云端双脑** | DeepSeek V4 + 腾讯混元 Hy3 | **语言智能**：会推理、会讲理由、能互相对辩 | 决策可解释，客户能看懂"为什么开这一单" |
| **本地双核** | Chronos-2 120M + Qwen3-8B | **数值智能 + 韧性保障**：出概率分布、常驻本机、断网仍在 | 云端全挂也不停摆（对应 9.4.4 降级车道） |

- 用 **`×`（乘号）而非 `+`**：强调云端推理与本地实证是**相乘的协同**（互相校验、互相兜底），不是四个模型简单堆叠投票。
- 「脑」对应思考与推理，「核」对应常驻算力与守护 —— 两个字各自准确，且对仗成立。

**副文分层（按展示空间选用，不得自创变体）**

| 层级 | 文案 | 使用位置 |
|---|---|---|
| **主副文** | `云端双脑 × 本地双核 · 四模型协同决策` | 登录页主视觉、关于弹窗、营销物料、导出报表页眉 |
| **锁定副文** | `云端双脑 × 本地双核 · 四模型协同` | `<Logo variant="horizontal" / "stacked" />` 锁定组合 |
| **紧凑副文** | `四模型协同决策` | 侧栏折叠态、移动端顶栏、窄容器 |
| **英文副文** | `Quad-model consensus engine` | 国际化界面、英文物料、代码注释与 README |
| **技术副文** | `DeepSeek V4 · 腾讯混元 Hy3 · Chronos-2 120M · Qwen3-8B` | 「关于」弹窗技术栈区、白皮书、技术文档 |

**三候选副文与采纳依据**

| 候选 | 文案 | 淘汰/采纳理由 |
|---|---|---|
| 甲 · 直陈式 | `DeepSeek × 腾讯混元 × Chronos-2 × Qwen3 · 四模型协同` | 借第三方品牌势能最强，但**过长**、模型迭代即失效、且直接并置第三方商标有暗示合作之嫌 → **降级为「技术副文」在关于弹窗使用** |
| 乙 · 灾备术语式 | `四模型共识 · 云地双活不断流` | 「双活」精准（云地都在跑、一边挂了另一边接管），技术客户秒懂；但非技术客户有理解门槛 → **淘汰**，其语义并入 9.4.4 降级车道说明 |
| **丙 · 形态对比式（★ 采纳）** | `云端双脑 × 本地双核 · 四模型协同决策` | 既讲清"四模型"这个量级卖点，又讲清"为什么要四个"；`双脑/双核` 为强意象，无行业黑话门槛；模型换代时副文无需改动 |

**上线红线（必须遵守，否则构成虚假宣传）**

1. **数量必须与实际运行一致**。截至本版本，实际运行为 **3/4**（DeepSeek V4 ✅、腾讯混元 Hy3 ✅、Chronos-2 ✅、**Qwen3-8B 未落地**）。
   - **启用条件**：「四模型」副文**须待 Phase 6 交付并通过混沌演练验收后方可对外使用**。
   - **过渡副文（Phase 6 前强制使用）**：`云端双脑 × 本地时序 · 三模型协同决策`
2. **不得称「四个大模型」**。Chronos-2 是 1.2 亿参数**时序基础模型**，不是 LLM。统一表述为「**四个 AI 模型**」或按分组分别表述，避免夸大。
3. **第三方商标合规**。提及 DeepSeek / 腾讯混元处，须标注「基于 XXX 公开 API 构建」，**不得暗示官方合作、认证或背书**；LOGO 中不得嵌入第三方商标。
4. **副文不承诺收益**。禁止在副文或任何品牌文案中出现「稳定盈利」「保本」「年化 X%」等表述（合规红线，见 10.5.3）。

### 10.2 设计令牌体系（统一风格的技术底座）

风格统一**不能靠"注意一点"，只能靠"物理上无法写错"**。做法：把 383 处硬编码全部收编为令牌，并用 lint 规则禁止新增。

#### 10.2.1 令牌分层

```css
:root {
  /* ── L1 品牌基色（唯一色源，其余全部派生）── */
  --brand-gold:        #E8B04B;   /* 主色：黄金 / 金融权威 */
  --brand-gold-bright: #FFD56B;   /* 高亮态 */
  --brand-gold-deep:   #E8901B;   /* 渐变末端 */
  --brand-ai-blue:     #4D9BFF;   /* 智能层：模型 / 数据 */
  --brand-ai-purple:   #B07BFF;   /* 智能层：本地模型 / Chronos */

  /* ── L2 语义色（业务含义，禁止直接用 L1）── */
  --sem-profit:   #2EE6A0;   /* 盈利 */
  --sem-loss:     #FF5C6C;   /* 亏损 */
  --sem-danger:   #FF3B4E;   /* 紧急处置 / 危险区 */
  --sem-warn:     #FFA53D;   /* 降级 L1/L2 */
  --sem-halt:     #8B5CF6;   /* MANUAL_HALT 人工停机 */
  --sem-ai:       var(--brand-ai-blue);
  --sem-gold:     var(--brand-gold);

  /* ── L3 表面层 ── */
  --surface-0: #070B14;  /* 页面底 */
  --surface-1: #0D1424;  /* 面板 */
  --surface-2: #111B30;  /* 卡片 */
  --surface-3: #16223C;  /* 卡片内嵌 / hover */
  --line-1:    #1F2D4A;  /* 分隔线 */
  --line-2:    #2A3A5C;  /* 强调边框 */

  /* ── L4 文字层 ── */
  --txt-1: #E6EDF7;  /* 主文字 */
  --txt-2: #8AA0C4;  /* 次要 */
  --txt-3: #5B6E91;  /* 提示 / 禁用 */

  /* ── L5 字体（收敛为 2 个字体栈，禁止第三个）── */
  --font-ui:  -apple-system, "PingFang SC", "Microsoft YaHei", "Segoe UI", sans-serif;
  --font-num: ui-monospace, "Cascadia Code", "JetBrains Mono", Consolas, monospace;

  /* ── L6 尺度 ── */
  --radius-sm: 6px;  --radius-md: 10px;  --radius-lg: 14px;
  --space-1: 4px; --space-2: 8px; --space-3: 12px;
  --space-4: 16px; --space-5: 24px; --space-6: 32px;
}
```

#### 10.2.2 强制规则

| 规则 | 说明 |
|---|---|
| **所有金额/手数/价格必须用 `--font-num`** | 等宽字体保证数字纵向对齐，这是金融界面的基本素养 |
| **涨跌色遵循中国习惯** | 盈利 = 绿（`--sem-profit`）、亏损 = 红（`--sem-loss`）。※ 本系统为交易盈亏语境，沿用现有绿盈红亏不变 |
| **业务色禁止直接引用 L1 品牌色** | 例：盈利数字必须写 `--sem-profit`，不能写 `--brand-ai-blue` |
| **新增代码零硬编码颜色** | 接入 `stylelint` 规则 `color-no-hex`，CI 阶段拦截 |
| **金色是稀缺资源** | `--brand-gold` 仅用于：LOGO、品牌名、关键盈利数字、主 CTA 按钮。滥用金色会让界面廉价 |

#### 10.2.3 383 处硬编码的收编策略
不做一次性大替换（风险高且无收益），采用**触碰即收编**：
1. 先落地 `:root` 令牌全集（纯新增，零风险）；
2. 任何组件因功能改动被打开时，**顺手把该文件内的硬编码换成令牌**；
3. 新增 `stylelint` 只对**新增行**报错（`--quiet-deprecation-warnings` + 增量 lint），避免存量报错淹没；
4. Phase 7 收尾时统计残余硬编码数，目标 < 30 处。

## 十一、客户端授权与激活体系（★ 商业化前提，原设计完全遗漏）

> 需求原话第一条即为「账号注册客户端的激活」。此前 v6 全文仅 2 处出现「激活」且均指 MT5 终端连接，**软件授权体系为零设计** —— 意味着客户拿到程序即可无限复制分发，商业模式不成立。

### 11.1 授权模型：绑定什么、限制什么

| 维度 | 取值 | 说明 |
|---|---|---|
| **绑定主体** | MT5 账号号码 + 机器指纹 | 双要素。仅绑机器 → 客户换电脑即失效体验差；仅绑 MT5 账号 → 一份授权可多机同跑 |
| **机器指纹** | 主板 UUID + 首个物理网卡 MAC + CPU ID 的 SHA256 | 单一要素易变（换网卡即失效），三要素取 **2/3 匹配即通过** |
| **账号配额** | `max_accounts`（授权允许的 MT5 账号数） | 对应"启动多少仓位取决于几个客户"的业务模型 |
| **有效期** | `valid_from` ~ `valid_until` | 支持试用（7 天）/ 年付 / 永久 |
| **功能档位** | `edition`：trial / standard / pro | pro 才开放跟单主号、本地模型降级车道 |

### 11.2 激活流程

```text
1. 客户安装客户端 → 首次启动检测到无本地授权文件
        ↓
2. 激活页要求输入：授权码（25 位分段码）+ MT5 账号号码
        ↓
3. 客户端采集机器指纹，向授权服务器 POST /license/activate
        ↓
4. 服务端校验：授权码存在 / 未被激活满配额 / 未过期
        ↓
5. 返回签名授权令牌（Ed25519 签名，含到期时间、配额、档位）
        ↓
6. 客户端落盘 license.dat（加密），后续启动本地离线校验签名
        ↓
7. 每 24h 静默向服务端续验一次（心跳），刷新令牌
```

**签名而非加密是关键**：授权令牌用 **Ed25519 非对称签名**，客户端只持有公钥。即使客户逆向出公钥也无法伪造令牌 —— 对称加密则一旦密钥泄露全线崩溃。

### 11.3 ★ 授权失效后的行为（必须与 9.4.2 红线一致）

**这是最容易设计错、且错了会出大事的地方。**

| 情形 | 允许的动作 | 禁止的动作 |
|---|---|---|
| 授权已过期 | 停止开新仓、前端持续提示续费 | ❌ **禁止强平客户持仓** |
| 授权服务器不可达 | 进入**离线宽限期**，一切照常 | ❌ 禁止因网络问题停止交易 |
| 超出账号配额 | 拒绝**新增**账号，已激活账号照常 | ❌ 禁止停用已在运行的账号 |
| 检测到授权码被多机盗用 | 冻结**新开仓**、告警运维介入 | ❌ 禁止自动强平 |

**离线宽限期 = 72 小时**。定这个值的理由：客户可能网络中断、可能授权服务器自身故障，而**交易系统因授权校验失败而停摆，造成的损失远大于盗版损失**。72h 足以覆盖一个周末 + 一个工作日的人工响应窗口。宽限期内前端显示黄色提示条，超过则降级为"只守不攻"（等同 9.4.4 的 L2 档位：不开新仓，出场逻辑与紧急处置窗口全部照常）。

> 与 9.4.2 同源的一条红线：**授权是商业契约问题，不是风控问题。软件可以拒绝继续服务，但不能处置客户的资产。**

### 11.4 防破解的现实边界（诚实说明）

**任何本地运行的软件都无法做到绝对防破解。** 本设计的目标不是"技术上不可能破解"，而是"破解成本高于购买成本"：

- ✅ 能挡住：直接复制目录到另一台机器、改系统时间绕过到期、简单的授权文件篡改
- ⚠️ 挡不住：有逆向能力者 patch 掉校验分支
- **真正的护城河不在客户端，而在服务端**：AI 决策依赖 DeepSeek / 腾讯混元云 API，密钥由平台侧持有并按授权状态发放（见 11.5）。**授权失效 → 云端不再下发有效密钥 → 破解版拿不到云模型，只剩本地模型跑 L2 档**。这比任何客户端加壳都有效。

### 11.5 密钥与鉴权规范（★ 补充遗漏）

**现状问题**：云模型 API Key 明文存放于 `backend/.env`。若客户端整包分发给客户，等于把平台的 API 账单交给客户。

| 项 | 规范 |
|---|---|
| 云模型密钥 | **绝不随客户端分发**。改为客户端携带授权令牌请求平台中转端点，由平台侧持有真实密钥 |
| 客户 MT5 密码 | 数据库中加密存储（`Fernet`，密钥由机器指纹派生），日志与前端一律脱敏为 `***` |
| 前端鉴权 | JWT，含 `user_id` 与 `license_edition`；所有账号级接口强制校验**资源归属**，防越权访问他人账号 |
| 审计日志 | 紧急处置、授权变更、策略参数修改三类操作写入不可变审计表 |

### 11.7 ★ 配置热更新的生效边界（补充遗漏）

客户在运行中修改本金 / 手数 / 风控参数时，**必须明确对在途持仓与新单分别如何适用**，否则会出现"改了参数但行为没变"或"已有持仓被新参数误伤"。

| 参数类型 | 对新开仓 | 对已有持仓 |
|---|---|---|
| `input_capital`（输入本金） | 下一周期立即生效 | **不重算已开仓手数**，仅影响后续加仓与风控比例 |
| `min_lot` / `max_lot` | 下一周期立即生效 | 不追溯，已开仓不被强制调整 |
| `max_position_lots`（总持仓上限） | 立即生效 | 若已超新上限：**只禁止加仓，不强制减仓** |
| SL/TP、追踪止损类 | 立即生效 | **立即重挂到所有在管持仓** |
| `follow_leader` 切换 | 立即生效 | 已有持仓归属不变，后续管理按新归属 |

**统一原则：收紧类参数不追溯已有持仓（避免误伤），出场类参数立即应用到全部持仓（保护客户）。** 每次配置变更写入审计日志并在前端事件流显示。

### 11.8 交易时段与休市（补充：代码已实现，文档纳管）

现有代码已具备 `market_analyzer.py` 周末判定、`trading.py` 休市跳过决策（零无效 API 调用）、`dashboard.py` 市场时钟（GMT+2/+3 夏令时）。纳入 V6 规范：

### 12.3 ★ 回归比对台（扼杀者模式的核心工具）

这是让重构"可验证"而非"祈祷不出事"的关键装置：

```text
1. 录制：在现有系统运行时，把每次决策的
   【输入快照】(行情/持仓/策略配置/AI决策)
   【输出结果】(最终手数/方向/SL/TP/是否被风控拦截)
   落盘为 fixtures（JSON，累积 200+ 真实样本）
        ↓
2. 回放：新 ExecutionController 以同样输入运行（dry-run，不下真实单）
        ↓
3. 断言：逐字段比对
   - 完全一致        → ✅ 通过
   - 不一致但可解释  → 人工确认后写入"预期差异清单"
   - 不一致且不可解释 → ❌ 阻断上线
```

**没有比对台就不允许切换任何账号到新路径。** 这条是硬约束。

### 12.4 扼杀者模式执行协议（Strangler Fig）

绝不"大爆炸式重写"。切换顺序固定：

| 步骤 | 动作 | 通过判据 |
|---|---|---|
| S1 | 新旧双跑，新路径 **dry-run 不下单**，只记录"它本来会怎么做" | 连续 24h 与旧路径一致率 100% |
| S2 | 切换 **1 个** 独立账号（`liumanchuan2`，已设 `follow_leader=0`）到新路径 | 连续 48h 无异常、净盈亏不劣于同期 |
| S3 | 切换剩余独立账号 | 同上 |
| S4 | 切换主号与跟号（最后，因为影响面最大） | 同上 |
| S5 | 旧路径代码标记 `@deprecated`，保留 2 周后删除 | —— |

**任一步骤失败 → 立即回退到上一步，不允许"带病前进"。**

### 12.5 数据库迁移单一入口（根治两套并存）

**决定：统一到 Alembic，废弃所有手写 `migrate_*.py`。**

理由：V6 新增字段量大（`input_capital`、`license` 系列表、`emergency_audit` 表、`state`/`last_reconciled_at` 等），手写脚本无版本链、无回滚、无幂等，必然出事。

| 规则 | 内容 |
|---|---|
| 唯一入口 | `alembic upgrade head`，禁止再写独立迁移脚本 |
| 存量脚本 | `migrate_add_quality_gates.py` 等移入 `backend/legacy_migrations/` 归档，不再执行 |
| 每次迁移前 | **强制备份** `wx_prod.dat` 到 `backups/wx_prod_YYYYMMDD_HHMMSS.dat` |
| 幂等性 | 每个迁移必须可重复执行不报错（`ADD COLUMN` 前先查 `PRAGMA table_info`） |
| 回滚 | 每个迁移必须实现 `downgrade()` |
| SQLite 限制 | SQLite 不支持 `DROP COLUMN` / `ALTER COLUMN`，涉及改列一律走"建新表→拷数据→改名"四步 |

### 12.6 回滚预案

| 层级 | 手段 | 恢复时间目标 |
|---|---|---|
| 代码 | 每个 Phase 完成即 `git tag`，回滚 = `git checkout <tag>` + 重启 supervisor | < 5 分钟 |
| 数据库 | 迁移前自动备份，回滚 = 停服务→换回备份文件→重启 | < 10 分钟 |
| 前端 | 保留上一版 `dist`，回滚 = 切软链 + 提示客户硬刷新 | < 3 分钟 |
| 运行时 | 人工紧急处置窗口（9.6）一键平仓 + `MANUAL_HALT` | 即时 |

**每个 Phase 开工前先打 tag，这是纪律不是建议。**

## 十四、验收标准

1. **手数可预期**：给定账号余额/输入本金/最小最大手数，手数计算链路可手算复现。
2. **同步一致**：主号任何平仓动作，跟号在 10s 内完成镜像；无重复、无遗漏。
3. **AI 透明**：每次决策展示 DS/HY/Chronos 三票、质量分 Q、仓位意图。
4. **风控兜底**：任何违反风控的下单请求被拦截并留下审计日志。
5. **扩展性**：账号数从 4 提升到 10+ 不需要改核心逻辑，只改线程池大小。
6. **不断流**：任一家云模型故障时系统**不停摆**而是降档运行（L1/L2），前端明确显示当前档位与手数系数；只有本地也不可用或行情脏污才进 L3。
7. **人可接管**：运维在任意时刻可对单仓/单账号/风险域/全体执行一键平仓，平仓后账号进入 `MANUAL_HALT` 且**系统不会自动恢复开仓**；每次处置留下含操作人、理由与逐单结果的不可变审计记录。
8. **视觉一致**：全站 LOGO 只来自 `<Logo />` 单一组件；任意两个板块的卡片圆角/内边距/字重/数字字体完全一致；新增代码零硬编码颜色（stylelint 拦截）；`favicon` 在浏览器标签页正常显示。
9. **版本可信**：`VERSION` 文件为唯一权威源，前端显示版本 == `/api/health` 返回版本 == `package.json` 版本；不一致时前端主动告警；每次发版有对应 `CHANGELOG` 条目与 `git tag`。
10. **合规可见**：登录页、侧栏、关于弹窗三处版权标识齐备，关于弹窗含明确风险提示与授权信息。
11. **品牌统一且属实**：全站软件全称与副文只来自 `src/brand/identity.js`，全局搜索无 `万象AI` / 旧品类词残留；**副文宣称的模型数量 == `PlatformHealthMonitor` 实际接入数量**（Phase 6 前必须显示三模型过渡副文）；「关于」弹窗决策引擎档位为实时值而非写死。
12. **账本不漂移**：每周期 `RECONCILING` 强制执行且不可跳过；人为在 MT5 手动开一单，系统应在下一周期检出并补录进本地账本而**不擅自平掉**；人为删除本地记录，系统应以 MT5 为准恢复。
13. **授权可控**：未激活客户端无法启动交易；授权过期后**只停开新仓、不强平持仓**；断开授权服务器 72h 内交易不受影响；超配额时拒绝新增账号但已有账号照常。
14. **改动可验证**：`pytest` 全绿方可提交；任何执行路径改动必须先过回归比对台（200+ 真实样本逐字段一致）；每个 Phase 有对应 `git tag` 与数据库备份，可在 10 分钟内回滚。

## 十五、一句话总结

> 把“AI 信号”和“交易执行”彻底拆开：AI 只输出高质量信号与仓位意图，执行控制器在策略风控的硬框架内完成开/加/减/平；所有账号通过 SignalBus 解耦同步；本金与手数权限链单一权威、前端可追溯；**并在最底层为运维保留一个随时可以人工接管的紧急出口。**
