1.2 核心设计缺陷

  • 无统一执行控制器：开单、加仓、减仓、平仓、对账各自为政，没有“账号级状态机”。
  • 风控与 AI 决策混排：AI 决策后又叠加多层门控（体制门、空头约束、置信惩罚），这些本应是风控兜底的职责，现在反而干扰 AI 信号。
  • 跟号逻辑与主号逻辑耦合：跟号既要做镜像，又要跑自己的风控，导致状态不一致。

2.2 关键原则

  1. 单一权威：每个账号的“有效本金”“有效手数范围”“当前持仓”只能有一个权威来源。
  2. 风控兜底最大：风控层拥有最终否决权；AI 与风控冲突时，风控赢，且必须留下审计日志。
  3. AI 只负责信号与意图：AI 输出方向、置信、仓位意图（open/add/reduce）、目标风险%；具体开不开、开多少由执行控制器在风控框架内执行。
  4. 账号级隔离：每个账号独立状态机、独立缓存、独立风控；账号之间只通过 SignalBus 传递 leader 信号。
  5. 多租户风险域隔离：一个账号 = 一个独立客户（详见 7.0）。风险与资金只在"同一客户的主号+跟号"内合并计算，跨客户绝不合并。平台层只熔断信号源，不干预客户持仓（详见 9.3 / 9.4）。
  6. 可观测：任何被拦截、被修改、被同步的事件都进入前端事件流，客户一眼看懂。

5.2 本金权限链（单一权威）

effective_capital =
    用户输入本金(input_capital)  if input_capital > 0
    else strategy.base_capital    if capital_source == "manual" and base_capital > 0
    else MT5 实时 balance
  • 用户输入本金权限最大：前端“本金入金”输入框一旦有值，所有手数/风控缩放以该值为准。
  • 未输入时：base_capital（手动模式）> balance（实时模式）。
  • 风控仍读取真实余额：日亏损、回撤熔断必须基于真实 equity/balance，不能基于输入本金造假。

5.3 手数权限链（单一权威）

raw_lots = f(effective_capital, signal_confidence, ATR, same_direction_count, intent)
allowed_lots = clamp(raw_lots,
                     hard_floor = user_min_lot,      # 单笔硬底，不可突破
                     hard_ceil  = user_max_lot)      # 单笔硬顶，不可突破
final_lots = min(allowed_lots,
                 risk_engine_max_single_lots,
                 risk_engine_max_position_lots_remaining)   # 同方向总持仓剩余额度
  • 用户输入的最低/最高手数是单笔硬边界，任何情况下不得突破。
  • 同方向总持仓上限 max_position_lots 是第二硬边界：已开仓 + 新开仓 ≤ max_position_lots。例：max_position_lots=1，第一单 BUY 0.2，AI 判断信号晴朗，第二单 BUY 0.5，总持仓 0.7 ≤ 1，允许。
  • 中间空间由行情决定：信号置信高、ATR 低、趋势强、意图为 add → AI 可在 [min_lot, max_lot] 内偏向上限给出更大的单笔；反之偏向低点。
  • AI target_risk_pct 在风控框架内可调高调低：上调受限于 max_risk_per_trade_pct 和单笔/总持仓硬顶；下调用于主动收缩风险。不是只能下调。

5.4 状态机转换

IDLE ──周期开始──▶ RECONCILING          (强制入口，不可跳过)
RECONCILING ──账本一致──▶ DECIDING
RECONCILING ──发现漂移──▶ REPAIRING ──修复完成──▶ DECIDING
DECIDING ──风控通过──▶ PLACING
PLACING ──下单成功──▶ OPEN
OPEN ──周期触发──▶ MANAGING
MANAGING ──出场条件满足──▶ EXITING
EXITING ──平仓完成──▶ IDLE

任意状态 ──人工紧急指令──▶ MANUAL_HALT   (插队，最高优先级)
MANUAL_HALT ──人工解除──▶ IDLE            (系统永不自动恢复)

任何状态遇到风控否决 → BLOCKED → 记录原因 → 回到 IDLE。

RECONCILING 是强制第一步（★ 补充：原状态机遗漏）

数据流 4a 定义了「反向对账」，但状态机原先直接 IDLE → DECIDING，等于允许系统在不知道自己真实持仓的情况下做决策 —— 这正是"有的开了有的没开、有的平了有的没平"的结构性来源。现修正为：每个周期必须先经过 RECONCILING，禁止跳过。

对账比对三组数据，任一不一致即进入 REPAIRING：

比对项权威源漂移典型成因
持仓列表（ticket 集合）MT5 实际持仓下单超时但实际成交、手动干预、跟号漏跟
每笔手数与方向MT5 实际持仓部分平仓未回写本地账本
SL/TP 实际挂载值MT5 实际持仓移损失败但本地已标记成功

权威源永远是 MT5，不是本地账本。 本地记录与 MT5 冲突时，无条件以 MT5 为准并改写本地。

REPAIRING 的四类修复动作：

漂移类型修复动作
MT5 有、本地无（孤儿单）补录进本地账本，纳入后续管理，不擅自平仓
本地有、MT5 无（幽灵单）删除本地记录，记审计事件
手数/方向不符以 MT5 为准覆写本地
SL/TP 缺失或不符按当前 ExitPlan 重新挂载
对账失败（如 MT5 查询超时）时不得进入 DECIDING，本周期直接跳过并告警 —— 宁可少做一单，不可盲开一单。

MANUAL_HALT 是唯一由自然人驱动进出的状态：进入时立即冻结开仓并逐单平仓，期间 AI 信号照常记录但执行层一律拒绝开新仓，剩余持仓的 SL/TP/SmartExit 仍继续生效。详见 9.6。

七、多账号扩展模型

7.0 业务前提：一个账号 = 一个客户（风险域边界定义）

这是全系统最重要的前提，任何风控/仓位/统计模块都必须遵守。

本系统的"多账号"是多租户（multi-tenant）业务形态，不是"同一个人开多个子账号"：

  • N 个交易账号 = N 个彼此独立的客户，资金无关联、法律主体独立。
  • N 完全由客户数量决定，是纯变量（可能是 1，也可能是 50+）。任何模块禁止假设固定账号数、禁止写死列表长度。
  • 唯一例外：同一客户可同时拥有 1 个主号 + 若干跟号（见 7.3）。这一组账号属于同一个客户，才可以合并计算风险。

由此，系统存在三级实体，风控作用域必须严格对应：

实体层级范围说明
账号（Account）单个 MT5 账号最小执行单元，独立 Worker、独立状态机
风险域（Risk Domain）同一 owner 的主号 + 跟号唯一允许合并计算资金风险的边界
平台（Platform）所有客户全体绝不合并客户资金，只做信号源健康与运营监控

7.1 并发粒度

  • 旧模型：每用户一个线程，内部串行处理所有账号。
  • 新模型：每个活跃交易账号一个 ExecutionController 实例，由账号级线程池调度。
  • 主号先决策，但通过 SignalBus 异步解耦，跟号不必等待主号完成全部流程。

7.2 10+ 账号扩展要点

  • 每个账号独立 Worker 进程（已具备）。
  • 每个账号独立数据库会话，禁止跨线程共享 SQLAlchemy Session。
  • 决策缓存按 account_id 隔离（已修复）。
  • SignalBus 事件 TTL + 幂等 key，防止事件积压。

7.3 主号与跟号权限覆盖规则

当用户显式指定某账号为主号(leader)，其他账号为跟号(follower)时：

权限项主号跟号
本金来源自身 effective_capital跟随主号的 effective_capital 与日 DD 计算口径
单笔手数范围自身 min_lot / max_lot跟随主号的 min_lot / max_lot
总持仓上限自身 max_position_lots跟随主号的 max_position_lots
日亏损/回撤熔断自身风控跟随主号的日 DD 逻辑与阈值
AI 辩论独立运行不独立辩论，直接消费主号 SignalBus 信号
出场动作独立生成并广播镜像主号的出场事件
  • 取消跟号关系后：跟号立即恢复自身策略配置（本金、手数范围、风控阈值），下一周期起按自身参数独立执行。
  • 技术实现：FollowerEngine 在启动时读取 leader_account_id；若存在，则从主号 AccountPortfolio 复制 EffectiveCapital 与 LotBounds 的计算口径，而不是复制主号余额数字（主号 $10k、跟号 $1k 时，跟号仍按 $1k 真实本金等比缩放，但边界比例与主号一致）。

九、策略风控兜底：最高权限

9.1 风控层职责

  • 点差、持仓笔数、持仓手数、同方向并发、日亏损、回撤、单笔风险、交易时段。
  • 任何一层未通过，交易被否决，并生成前端可见的“风控拦截”事件。

9.2 与 AI 的冲突规则

场景处理
AI 要开仓，风控通过正常执行
AI 要开仓，风控否决否决，记录原因，不改变持仓
AI 要加仓，风控提示仓位已满降级为 reduce 或 hold
AI 要平仓，风控通过正常执行
风控触发硬止损/熔断无视 AI，直接平仓，记录为“风控兜底”
人工紧急指令（L-M）无视 AI、无视风控评估、插队执行，最高优先级（见 9.6）

L-B 风险域级同一客户的主号 + 全部跟号✅ 合并该客户名下全部账号停止开仓
L-C 平台级全体客户❌ 绝不合并只熔断信号发布，不动任何客户持仓

为什么绝不做跨客户资金合并熔断：

  1. 资金无关联：客户 A 亏损与客户 B 毫无关系。用 A 的亏损去停 B 的单，等于无故剥夺 B 的交易机会，会直接引发投诉与赔付纠纷。
  2. 合规红线：不同客户资金必须独立核算。合并风控口径 = 把独立账户当成一个资金池处理。
  3. 阈值不可定义：日损"总额"会随客户数线性膨胀。10 个客户和 100 个客户的"合计亏损线"没有任何可比性，参数无法设定。

风险域级（L-B）合并的合法性：主号 + 跟号本就是同一客户的资金，且跟号本就继承主号的本金口径与日 DD 逻辑（7.3），合并计算是自洽的。

★ 补充：以上 L-A / L-B / L-C 三层全部是「系统自动」判定。系统之外还存在第四个授权来源 —— 人。

授权来源判定者可否处置客户持仓
L-A / L-B算法（阈值触发）系统✅ 在客户已授权的风控规则内
L-C 平台熔断算法（健康度触发）系统❌ 绝对禁止（见 9.4.2）
L-M 人工紧急处置自然人主动按下运维人员✅ 可以，且优先级最高（见 9.6）

L-M 不是风控规则，是人工干预通道。系统永远不会自己触发它。详见 9.6。

9.4 平台级熔断：熔的是"信号源"，不是客户资金

虽然禁止合并客户资金，但所有客户消费同一个 AI 信号源（XAUUSD），这构成真实的系统性风险 —— 风险来源不是资金相关性，而是信号源相关性。信号源一旦失灵，全体客户会同时亏损，这是平台方的责任风险。

触发条件（全部基于信号源自身健康度，与任何客户资金无关）：

触发项判据
信号连败平台级信号（跨客户去重后，非订单数）连续 N 次以止损收场
模型不可用DeepSeek / 混元 / Chronos 任一持续超时或返回异常
行情异常行情源断线、tick 停滞、点差异常扩大
鞭锯识别单位时间内方向反转次数超阈

9.4.1 五个真实触发场景（判据的具体形态）

场景 A — 云模型半瘫（最高频）

凌晨 DeepSeek 服务端 503 / 欠费停服 / 限流。DS 与 HY 权重各 0.5，DS 一挂，裁决实际退化为「混元一人说了算」，若代码给缺席方填中性默认值参与加权，等于半个大脑在下单。此刻全体客户会同时按这个瘸腿决策开仓。

场景 B — 数据事件点差爆炸

北京时间 20:30 非农 / CPI 公布瞬间，XAUUSD 点差从 ~20 跳到 400+。AI 拿到的是失真价格，算出的 SL/TP 距离全错，任何客户此刻进场都是先亏几十美金起步。

场景 C — 报价冻结（最阴险，不报错）

MT5 连接显示「在线」，但 tick 停止更新，同一 bid/ask 卡住 90 秒。Chronos 用这段死数据出的 P10/P50/P90 全是垃圾，SMC 会误判为「极度盘整」。系统不会抛异常，它会自信地给出一个完全错误的信号。

场景 D — 信号连败（计数口径是关键）

必须按信号 ID 去重：同一信号无论被多少客户执行，胜负只算 1 次。若按订单计数，10 个客户跟一个信号 → 一次失败产生 10 笔亏损单 → 「连败 3 次」瞬间触发，客户越多越容易误熔断。这与已作废的「跨账号合计损失线」是同一类错误（阈值随客户数膨胀），不得重犯。

场景 E — 方向鞭锯

DS/HY 在 0.5 低置信下反复翻转（BUY→SELL→BUY）。短时高频翻向说明模型已在噪声中迷失，属模型状态问题而非某个客户的问题（本项目已有实证亏损记录）。

触发后动作（关键：只作用于信号层）：

  • ✅ 停止发布新开仓信号 —— 所有客户都不再收到新单；
  • ✅ 不强平任何客户持仓 —— 已有仓位交回各账号自身风控（SL/TP/SmartExit/篮子兜底）处理；
  • ✅ 前端全局横幅告警 + 运营侧通知；
  • ✅ 恢复需人工确认，或健康度连续 M 个周期正常后自动恢复。
一句话：平台熔断只关水龙头，不抽走客户已经接到桶里的水。

9.4.2 为什么只能停信号、不能强平（红线依据）

类比：交易所熔断 = 暂停撮合，不是替你把股票卖掉；替客户处置资产是券商强平，性质完全不同。本平台的角色是「信号供应商」，只能停止供货。

红线理由
已开仓是客户资产平台无权处置，强平引发赔付纠纷与合规风险
客户自设规则仍有效SL/TP/SmartExit/篮子是客户已授权的处置规则，熔断期间照常运行
客户手动权不受限熔断期间客户仍可自行操作本人账号

9.4.3 与「多交易多赚钱」铁律不冲突

熔断只在大脑故障 / 数据脏污时触发，此刻信号期望为负 —— 这是拒绝在故障状态下瞎下单，不是「过滤好信号」。二者本质区别：

  • ❌ 多层过滤：好信号被门槛砍掉 → 交易笔数↓、利润↓（已多次验证失败）
  • ✅ 故障熔断：坏信号根本不该产生 → 保护利润，且持续时间为分钟级（API 恢复即恢复），非常态

因此熔断不计入「过滤」范畴，不受「提准非拦截」铁律约束。

9.4.4 ★ 降级车道：熔断不该只有「停」一个档位（本地模型兜底）

问题：9.4 定义的熔断是二值的 —— 要么全绿正常跑，要么全红停摆。但现实中最高频的故障（场景 A：单家云模型 503/限流）并不需要「全停」，那是过度反应，会白白损失交易笔数，违背「多交易多赚钱」。

业界标准做法：LLM Waterfall Pattern（瀑布降级）—— Tier1 主 API → Tier2 备用 → Tier3 本地模型兜底。核心是「渐进降级（graceful degradation）」而非「二值开关」。多家生产实践一致给出的降级链形态为：缓存 → 主模型+重试 → 备用模型 → 本地小模型 → 静态兜底。

9.6 ★ 人工紧急处置窗口（Operator Emergency Console）

定位：这不是风控规则，是给运维人员的人工干预通道。系统永远不会自己按这个按钮。<br>算法负责 7×24 自动运行，人负责在算法覆盖不到的异常里做最终决断。任何成熟的自动交易系统都必须给"人"留一个出口。

9.6.1 与 9.4.2「平台不得强平」是否矛盾？—— 不矛盾，区别在授权来源

9.4.2 禁止的9.6 允许的
谁决定算法自动判定自然人主动按下
是否可追责到人否（无人授权）是（身份+IP+时间+理由全留痕）
客户视角"系统莫名其妙把我平了""平台运维在异常中做了紧急处置，有记录可查"
一句话：禁止的是「机器擅自动客户的钱」，不是禁止「人在紧急情况下负责任地处置」。

这在行业里是监管强制项，不是可选功能：

  • 美国 SEC Rule 15c3-5（市场准入规则）要求具备直接市场准入的机构必须有人工 kill switch；
  • 欧盟 MiFID II RTS 6 明确要求算法交易系统必须具备 kill functionality，可即时撤销未成交订单并中止交易；
  • 各大交易所（CME/ICE）均提供并要求会员配置 kill switch。

所以「一键平仓」不是我们的额外发明，是商业化交易系统的准入门槛。

  • 紧急指令是最高优先级消息，插队到账号状态机队首，无视当前周期正在做什么（哪怕正在 DECIDING/PLACING）。

10.2.3 383 处硬编码的收编策略

不做一次性大替换（风险高且无收益），采用触碰即收编：

  2. 任何组件因功能改动被打开时，顺手把该文件内的硬编码换成令牌；
  3. 新增 stylelint 只对新增行报错（--quiet-deprecation-warnings + 增量 lint），避免存量报错淹没；
  4. Phase 7 收尾时统计残余硬编码数，目标 < 30 处。

十一、客户端授权与激活体系（★ 商业化前提，原设计完全遗漏）

需求原话第一条即为「账号注册客户端的激活」。此前 v6 全文仅 2 处出现「激活」且均指 MT5 终端连接，软件授权体系为零设计 —— 意味着客户拿到程序即可无限复制分发，商业模式不成立。

11.1 授权模型：绑定什么、限制什么

维度取值说明
绑定主体MT5 账号号码 + 机器指纹双要素。仅绑机器 → 客户换电脑即失效体验差；仅绑 MT5 账号 → 一份授权可多机同跑
机器指纹主板 UUID + 首个物理网卡 MAC + CPU ID 的 SHA256单一要素易变（换网卡即失效），三要素取 2/3 匹配即通过
账号配额max_accounts（授权允许的 MT5 账号数）对应"启动多少仓位取决于几个客户"的业务模型
有效期valid_from ~ valid_until支持试用（7 天）/ 年付 / 永久
功能档位edition：trial / standard / propro 才开放跟单主号、本地模型降级车道

11.2 激活流程

1. 客户安装客户端 → 首次启动检测到无本地授权文件
        ↓
2. 激活页要求输入：授权码（25 位分段码）+ MT5 账号号码
        ↓
3. 客户端采集机器指纹，向授权服务器 POST /license/activate
        ↓
4. 服务端校验：授权码存在 / 未被激活满配额 / 未过期
        ↓
5. 返回签名授权令牌（Ed25519 签名，含到期时间、配额、档位）
        ↓
6. 客户端落盘 license.dat（加密），后续启动本地离线校验签名
        ↓
7. 每 24h 静默向服务端续验一次（心跳），刷新令牌

签名而非加密是关键：授权令牌用 Ed25519 非对称签名，客户端只持有公钥。即使客户逆向出公钥也无法伪造令牌 —— 对称加密则一旦密钥泄露全线崩溃。

11.3 ★ 授权失效后的行为（必须与 9.4.2 红线一致）

这是最容易设计错、且错了会出大事的地方。

情形允许的动作禁止的动作
授权已过期停止开新仓、前端持续提示续费❌ 禁止强平客户持仓
授权服务器不可达进入离线宽限期，一切照常❌ 禁止因网络问题停止交易
超出账号配额拒绝新增账号，已激活账号照常❌ 禁止停用已在运行的账号
检测到授权码被多机盗用冻结新开仓、告警运维介入❌ 禁止自动强平

离线宽限期 = 72 小时。定这个值的理由：客户可能网络中断、可能授权服务器自身故障，而交易系统因授权校验失败而停摆，造成的损失远大于盗版损失。72h 足以覆盖一个周末 + 一个工作日的人工响应窗口。宽限期内前端显示黄色提示条，超过则降级为"只守不攻"（等同 9.4.4 的 L2 档位：不开新仓，出场逻辑与紧急处置窗口全部照常）。

与 9.4.2 同源的一条红线：授权是商业契约问题，不是风控问题。软件可以拒绝继续服务，但不能处置客户的资产。

11.4 防破解的现实边界（诚实说明）

任何本地运行的软件都无法做到绝对防破解。 本设计的目标不是"技术上不可能破解"，而是"破解成本高于购买成本"：

  • ✅ 能挡住：直接复制目录到另一台机器、改系统时间绕过到期、简单的授权文件篡改
  • ⚠️ 挡不住：有逆向能力者 patch 掉校验分支
  • 真正的护城河不在客户端，而在服务端：AI 决策依赖 DeepSeek / 腾讯混元云 API，密钥由平台侧持有并按授权状态发放（见 11.5）。授权失效 → 云端不再下发有效密钥 → 破解版拿不到云模型，只剩本地模型跑 L2 档。这比任何客户端加壳都有效。

11.5 密钥与鉴权规范（★ 补充遗漏）

现状问题：云模型 API Key 明文存放于 backend/.env。若客户端整包分发给客户，等于把平台的 API 账单交给客户。

项规范
云模型密钥绝不随客户端分发。改为客户端携带授权令牌请求平台中转端点，由平台侧持有真实密钥
客户 MT5 密码数据库中加密存储（Fernet，密钥由机器指纹派生），日志与前端一律脱敏为 ***

11.7 ★ 配置热更新的生效边界（补充遗漏）

客户在运行中修改本金 / 手数 / 风控参数时，必须明确对在途持仓与新单分别如何适用，否则会出现"改了参数但行为没变"或"已有持仓被新参数误伤"。

参数类型对新开仓对已有持仓
input_capital（输入本金）下一周期立即生效不重算已开仓手数，仅影响后续加仓与风控比例
min_lot / max_lot下一周期立即生效不追溯，已开仓不被强制调整
max_position_lots（总持仓上限）立即生效若已超新上限：只禁止加仓，不强制减仓
SL/TP、追踪止损类立即生效立即重挂到所有在管持仓
follow_leader 切换立即生效已有持仓归属不变，后续管理按新归属

统一原则：收紧类参数不追溯已有持仓（避免误伤），出场类参数立即应用到全部持仓（保护客户）。 每次配置变更写入审计日志并在前端事件流显示。

十四、验收标准

  1. 手数可预期：给定账号余额/输入本金/最小最大手数，手数计算链路可手算复现。
  2. 同步一致：主号任何平仓动作，跟号在 10s 内完成镜像；无重复、无遗漏。
  3. AI 透明：每次决策展示 DS/HY/Chronos 三票、质量分 Q、仓位意图。
  4. 风控兜底：任何违反风控的下单请求被拦截并留下审计日志。
  5. 扩展性：账号数从 4 提升到 10+ 不需要改核心逻辑，只改线程池大小。
  6. 不断流：任一家云模型故障时系统不停摆而是降档运行（L1/L2），前端明确显示当前档位与手数系数；只有本地也不可用或行情脏污才进 L3。
  7. 人可接管：运维在任意时刻可对单仓/单账号/风险域/全体执行一键平仓，平仓后账号进入 MANUAL_HALT 且系统不会自动恢复开仓；每次处置留下含操作人、理由与逐单结果的不可变审计记录。
  8. 视觉一致：全站 LOGO 只来自 <Logo /> 单一组件；任意两个板块的卡片圆角/内边距/字重/数字字体完全一致；新增代码零硬编码颜色（stylelint 拦截）；favicon 在浏览器标签页正常显示。
  9. 版本可信：VERSION 文件为唯一权威源，前端显示版本 == /api/health 返回版本 == package.json 版本；不一致时前端主动告警；每次发版有对应 CHANGELOG 条目与 git tag。
  10. 合规可见：登录页、侧栏、关于弹窗三处版权标识齐备，关于弹窗含明确风险提示与授权信息。
  11. 品牌统一且属实：全站软件全称与副文只来自 src/brand/identity.js，全局搜索无 万象AI / 旧品类词残留；副文宣称的模型数量 == PlatformHealthMonitor 实际接入数量（Phase 6 前必须显示三模型过渡副文）；「关于」弹窗决策引擎档位为实时值而非写死。
  12. 账本不漂移：每周期 RECONCILING 强制执行且不可跳过；人为在 MT5 手动开一单，系统应在下一周期检出并补录进本地账本而不擅自平掉；人为删除本地记录，系统应以 MT5 为准恢复。
  13. 授权可控：未激活客户端无法启动交易；授权过期后只停开新仓、不强平持仓；断开授权服务器 72h 内交易不受影响；超配额时拒绝新增账号但已有账号照常。
  14. 改动可验证：pytest 全绿方可提交；任何执行路径改动必须先过回归比对台（200+ 真实样本逐字段一致）；每个 Phase 有对应 git tag 与数据库备份，可在 10 分钟内回滚。

十五、一句话总结

把“AI 信号”和“交易执行”彻底拆开：AI 只输出高质量信号与仓位意图，执行控制器在策略风控的硬框架内完成开/加/减/平；所有账号通过 SignalBus 解耦同步；本金与手数权限链单一权威、前端可追溯；并在最底层为运维保留一个随时可以人工接管的紧急出口。
