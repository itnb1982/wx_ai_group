2.1 发现的关键数据 bug

数据库 C:/WXDB/wx_prod.dat 中：

  • 4 个真实 MT5 账号（liumanchun1/2/3/4）全部属于交易用户 itnb（6f50aea4…）
  • 但 strategy_configs 策略行却全部属于另一个用户 probe（6af9b283…），且有一条孤儿 fake-account-id 行

自动循环按 itnb 查策略（get_or_default_strategy 用 (mt5_account_id, user_id) 双过滤），匹配不到任何行 → 全员回退默认 follow_leader=True。

后果：

  1. 独立风控开关（follow_leader=False）从未被读取——你在 UI 里改的开关，运行循环根本读不到；
  2. 每账号风控参数（basket_tp_amount / max_positions / L3 等）从未被应用——全员用默认值。

也就是说：系统代码完全支持"主号带跟号 + 部分账号独立风控"，但因为配置被孤儿在错误用户下，实际全在跑默认镜像。这正好解释了你"各自仓位单独执行是否健康"的疑问——之前根本没真正独立执行过。

三、方向一：AI 进化（已修复，与只读 DB 解耦）

3.1 "越跑越笨"的真正原因

后端日志满屏 (sqlite3.OperationalError) attempt to write a readonly database：

  • 反向对账落库失败（成交平仓无法写库）
  • ai_scanner 写库失败（每轮扫描都失败）
  • key_pool 写库失败（token 统计丢失）

SQLite 被 Windows Defender 实时防护在长连接持有时周期锁死。我的脚本能短时写入（之前改策略成功），但长驻后端进程持续持有文件句柄 → 写库失败。

影响：成交平仓无法落库 → AI 注入看到的"最近成交"是陈旧空数据（日志显示"近 08-05 18:53 合计盈亏 +0.00$"），这正是"开单不聪明、盈利无变化"的直接技术根因之一。

旁证：日志里"已注入最近 15 笔真实成交"其实每周都在跑——说明代码已把成交喂给 AI；但喂的是被锁死 DB 里的陈旧空数据，等于"喂了但喂的是空的"。

3.2 另一处笔误 bug（_len）

debate_engine.py 日志行写成 _len(_lessons)（多了下划线）→ NameError，被 except 捕获后误报"memory_bank 注入跳过"。实际历史经验已在报错前注入，故属误报，但误导排查。已改为 len(_lessons)。

3.3 修复动作

  1. 成交记忆改走内存环形缓冲（系统既有设计 ai_memory._trade_buf，永远可写）：
  • ai_memory.push_trade_event 新增 pnl / ticket / open_price / close_price / reason 结构化字段；
  • trade_executor._push_feed 及平仓/开仓调用透传这些字段（每笔真实成交实时入内存）；
  • debate_engine 注入逻辑优先读内存缓冲，DB 仅作"进程重启后暂无数据"时的回退。
  • 效果：无论 Defender 是否锁库，AI 都能看到自己最近的真实盈亏 → 持续学习，根治"越跑越笨"。
  1. 修复 _len 误报。
