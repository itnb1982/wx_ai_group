## 一、用户的核心担忧

> 盈利单在仓的时候，AI 会不会启动走追踪止损 / TP？如果他不启动，那不是由赚钱变成亏钱了吗？

这正是此前 M1 出场 Agent 接管持仓时存在的**致命漏洞**：AI 一旦接管，浮盈单可能失去确定性保本。

---

## 二、根因（漏洞定位）

`trade_executor._manage_positions` 原代码逻辑：

```python
plan = exit_decisions.get(str(pos.get("ticket")))   # M1 对该持仓的决策
if plan is None:
    plan = smart_evaluate_position(...)              # 无 M1 → 用规则引擎
# 有 M1 的 plan 时：直接用它，跳过 smart_evaluate_position 整段！
```

**问题**：M1（AI 出场 Agent）通过缓存 / 粘滞机制返回某笔持仓的 `plan`，即使只是 `action=hold, new_sl=None`（命中缓存、不移动止损），也会让规则引擎 `smart_evaluate_position` **整段被跳过**——包括：

- 早期保本（浮盈 ≥ 0.3×ATR 时把 SL 移到开仓价 + 缓冲）
- TP1/TP2 后的追踪止损

后果：**浮盈单在 0~0.3×ATR 这个窗口内，M1 返回 hold 无 new_sl 时，没有任何确定性保本** → 价格回吐就可能由赚变亏。

---

## 三、修复方案（硬地板）

原则：**规则引擎的保本 / 追踪 SL 永远先计算、永远应用，不可被 M1 跳过；M1 只能给出「更锁利」的 SL 才覆盖**。

### 1. 新增模块级合并函数 `_merge_hard_floor_sl`

```python
def _merge_hard_floor_sl(*, pos_type, current_sl, rule_new_sl, m1_new_sl):
    # 候选集 = {规则引擎SL, M1的SL, 当前SL} 中有效者
    #   buy 单：取最大 SL（最锁利，离入场最远、留利最多）
    #   sell 单：取最小 SL（最锁利）
    # 最优者等于当前 SL → 返回 None（不移动，避免无意义 modify）
```

### 2. 改写 `_manage_positions` 持仓循环入口

```python
# ① 永远先算规则引擎（含保本/追踪 SL）—— 硬地板
rule_plan = smart_evaluate_position(...)
rule_new_sl = rule_plan.get("new_sl")

plan = exit_decisions.get(str(pos.get("ticket")))
if plan is None:
    plan = rule_plan                      # 无 M1 → 完全用规则引擎（原逻辑）
else:
    # 有 M1 → action/reason 用 M1；new_sl 走硬地板合并
    merged_sl = _merge_hard_floor_sl(
        pos_type=..., current_sl=..., rule_new_sl=rule_new_sl, m1_new_sl=plan.get("new_sl"))
    plan = dict(plan); plan["new_sl"] = merged_sl
```

### 3. 设计要点

- **保本确定性恢复**：只要规则引擎算出更锁利的保本 / 追踪 SL，就一定应用，无论 M1 是否接管。
- **不削弱 AI**：M1 的反向 / 分批 / 全平决策完全保留；仅当 M1 给出比规则引擎更优（更锁利）的追踪 SL 时才覆盖。
- **跟号兼容**：信号塔分流逻辑下，仅主号（`_is_leader=True`）走完整 AI 出场 + 硬地板；跟号通过 `publish_leader_exit` 镜像主号广播的移损 / 平仓，闭环一致。

## 四、验证结果

### 单测 `test_hardfloor.py` —— 8 / 8 PASS

| 场景 | 结果 |
|---|---|
| buy 保本地板不被 M1(None) 覆盖 | ✅ 取规则引擎 2000.5 |
| buy M1 更优追踪覆盖规则 | ✅ 取 M1 2010.0 |
| buy 双方无 SL → 不动 | ✅ None |
| sell 保本地板 | ✅ 取规则引擎 1999.5 |
| sell M1 更优追踪覆盖 | ✅ 取 M1 1990.0 |
| 等于当前 SL → 不动 | ✅ None |
| 当前 SL=0 → 用规则引擎保本 | ✅ 2000.5 |
| 未知类型 → None | ✅ None |

### 集成测试 `test_hardfloor_integration.py` —— 3 / 3 PASS（mock MT5 / DB）

| 场景 | 结果 |
|---|---|
| **M1 接管 hold 无 new_sl + 浮盈 0.3ATR → 保本地板应用** | ✅ `modify_sl_tp(ticket=12345, sl=2000.5)` 被调用 |
| M1 更优追踪覆盖规则 | ✅ sl=2010.0 |
| 无持仓安全返回 | ✅ 不调用 modify / close |

**核心结论**：此前"M1 接管 → 浮盈单失去确定性保本"的漏洞已被钉死——即使 M1 返回 hold，规则引擎算出的保本 SL 仍会被强制应用。
