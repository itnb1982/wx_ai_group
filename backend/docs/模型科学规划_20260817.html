四、本轮落地：TimesFM-2.5 风险区间交叉验证（新增 ts_cross_validate 服务）

设计依据（不是拍脑袋）：

  • TimesFM 方向 acc 50.0%（无用），但它独立预测的分位数与 Chronos-2 是两把不同的尺子
  • 两把尺子一致 → 区间可信 → 信号质量 q+0.05（提准）
  • 两把尺子显著分歧 → 不确定性高 → q-0.10 + 止盈天花板收紧到较保守端（降损）
  • 铁律：只调质量分和止盈，绝不做开仓拦截（提准非拦截红线）

性能实测：常驻单例加载 3.2s（首轮）→ 纯推理 0.10s/次 → 缓存 120s

（指纹=末16根价格+长度），决策循环 60-90s 完全放得下。

改动清单：

  • 新增 app/services/ts_cross_validate.py（单例+缓存+超时静默降级）
  • app/services/meta_quality.py：_evaluate_core 增加 cross 参数；同步/异步入口接入
  • 单测 tests/test_ts_cross_validate.py 6 项全过（真实推理验证分歧度语义）

端到端验证（真实行情 4391.72 收盘）：

  • Chronos 窄区间（乐观 0.2%）→ TimesFM 分歧 0.613 → mid（谨慎）
  • Chronos 宽区间（1%）→ 分歧 0.277 → high（区间可信）
  • 语义正确：Chronos 越乐观、分歧越大，系统越谨慎 ✓

六、Time-MoE：为什么"装好没通电"——接口不兼容（技术实锤）

  • 权重在 models/timemoe-200m（config + safetensors + 自写 modeling）
  • transformers 5.14 有 4 处 API 断点：seen_tokens（改名 get_seq_length）、

from_legacy_cache（移除）、get_usable_length（移除）、

_extract_past_from_model_output（新增调用）→ 模型代码是 4.x 时代写的

  • 逐层 monkey-patch 是在生产全局 DynamicCache 类上挂补丁 → 有污染风险，拒绝
  • 正确解法：等官方 release 或建 transformers4 隔离 venv（约 10min，收益低暂缓）
